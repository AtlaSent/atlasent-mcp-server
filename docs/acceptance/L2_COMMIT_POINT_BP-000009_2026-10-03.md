## What kind of commit point this is

This is **simulated harness evidence about a client-side commit point**, not a
native provider-effect commit point.

- The commit point is the MCP server's `executeGoverned`. The runtime verifies
  and consumes the permit. The very next event in the single ordered
  runtime+provider log is the governed provider write, which carries only the
  provider's own base-sha precondition.
- The provider never sees or checks the permit. Verify and write are two calls.
  Their adjacency is shown in the harness's event log. The provider does not
  enforce it.
- A native provider-effect commit point, where the provider checks
  authorization atomically as part of applying the change, is not shown here.
- Both the AtlaSent runtime and the provider are simulations (below).

## The adjacency rule (R6, R6b)

Every `provider.mutation` in every scenario must be **immediately** preceded by
a successful `runtime.verify`. Nothing may sit between them: no provider read,
no provider state change, no other runtime call, and no second write reusing
the same verify. R6 applies this to the MCP tool path. R6b applies it to every
scenario, including the commit-point-level scenarios where adapter mutants run.
Out-of-band provider changes are logged as `provider.state_change`, so the rule
can see them.

Clean sequence for the tool path:

```
provider.read > runtime.identity_mint > runtime.seal > runtime.evaluate >
runtime.permit_issued > provider.read > runtime.verify > provider.mutation >
provider.read > provider.read
```

The `provider.read` before `runtime.verify` is the stale-target check (E1). It
runs before the permit is spent. The two reads after the write are the effect
observation.

## The harness fails when the binding is broken

| Mutant | Caught by |
|---|---|
| `verify_bypassed` | R5–R10, R12, R6b |
| `payload_binding_removed` | R2, R5–R7, R9, R12, R13 |
| `replay_possible` | R7, R8 |
| `deny_reaches_provider` | R11, R6b |
| `execution_inferred_from_authorization` | R13b (both) |
| `provider_read_between_verify_and_mutation` (hostile, #794) | R6b only |
| `provider_state_change_between_verify_and_mutation` (hostile, #794) | R6b only |

The two hostile mutants change nothing else. The read is harmless, and the
state change touches a different file, so the provider's base-sha precondition
still passes. The test asserts that each one fails **only** R6b, and that the
superseded rule (last runtime call before the write is a verify) does **not**
see either. That is the positive control: the mutants reproduce the gap #794
names.

Mutations of the rule itself, each run against the suite:

- Skip intervening provider reads: the read mutant and the rule's unit test
  fail.
- Restore the superseded last-runtime-call rule: both hostile mutants and the
  unit test fail.

Mutation of the real source: inserting `adapter.readState()` after verify in
`executeGoverned` fails R6 and R6b in every scenario that writes.
